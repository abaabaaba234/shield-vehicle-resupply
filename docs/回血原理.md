# 回血是怎么实现的（以及以前的扫描为什么删掉了）

## 一句话
游戏扣血用的是**它自己另存的一份血量**，不是 Health 记录里的当前值。v0.12 靠在内存里扫描找那份拷贝，
扫的时候会拖帧；v0.13 改成直接打开**游戏自带的回血开关**，让游戏自己把两份血量一起涨，扫描代码全部删除。

## 问题：修好的血一挨打就掉回去
mod 改血是改 Health 组件记录里的当前值（主血量 `+0x14`、部位血量 `+0xF8 + 4×i`）。
但实测游戏扣血时不是从这个值往下减，而是：

```
受伤后的血量 = 游戏自己另存的“上次受伤后”的血量 − 伤害
```

例如机甲：1543 → 在护盾里修到 1800 → 挨一下变成 1444（= 1543 − 99）。
mod 加的 257 点只写进了记录，游戏那份拷贝还是 1543，一挨打就盖回来。

## v0.12 的做法：全内存扫描找那份拷贝（已删除）
1. 载具第一次在护盾里回血时，扫描进程里所有可读写的私有内存（约 5 GB），
   记下等于“修前血量”的地址、以及“连续 N 个值 = 各部位修前血量”的整段部位数组。
2. 之后每挨一下打，只留下跟着变成新血量的地址，一两下之后基本只剩真正的那几个。
3. 以后每次回血，把这几个地址也改成新血量。

为什么会卡：扫描 5 GB 大约要 4.5~4.7 秒，而 mod 跑在游戏的 Lua 更新回调里，回调不返回游戏这一帧就画不出来。
v0.12g 起拆到每帧做（每帧 3~12 毫秒），大约 15~20 秒扫完，不卡了，但代价是：
扫完之前挨的打、以及扫完用来确认的第一下，修的血仍然会掉回去；换局、重新呼叫载具都要重新扫。

## v0.13 的做法：打开游戏自带的回血
字段布局来自 [filediver](https://github.com/xypwn/filediver) 的 `datalibrary`（游戏明文数据）：

| 偏移 | 字段 | 说明 |
|---|---|---|
| `+0x00` | `Health` | 最大血量（v0.12 已在游戏内确认，配置表里就是它） |
| `+0x04` | `HeathChangerate` | 未受伤时每秒回多少血（游戏里的拼写少一个 l） |
| `+0x08` | `HealthChangerateDisabled` | **回血开关**：1 = 关闭回血 |
| `+0x0C` | `HeathChangerateCooldown` | 受伤后等几秒开始回血 |
| `+0x10` | `RegenerationSegments` | 回血段数 |
| `+0x14` | `RegenerationChangerate` | 回血阶段每秒回多少血 |
| `+0x208` | `DamageableZones[38]` | 部位数组，步长 `0x228`；部位名 `+0x60`、部位上限 `+0xE8`（v0.12 已在游戏内确认） |

配置表按“单位资源”共享（每种载具一条记录，地址由实体的 Health 组件反查得到），所以 mod：

- 载具停在罩子里、而且**本机有权威**（`authority_only`）时，把这条记录打开：
  `HeathChangerate = 上限 × exo_heal / tank_heal / frv_heal`（单位是“每秒多少点血”）、
  `HealthChangerateDisabled = 0`、`HeathChangerateCooldown = cooldown`、
  `RegenerationSegments = native_segments`、`RegenerationChangerate = 同一个速率`。
- 载具离开罩子、护盾结束、`off` / `heal off` 时，把这些字段**写回原值**。
- 写之前先检查配置头像不像 `HealthComponent`（上限 > 0、开关字节是 0/1、速率/冷却是有界的正数…），
  不像就一个字节都不写，日志记一条 `native: … 的配置头不像 HealthComponent`。
- 写用的是写前比对、写后读回的 `WriteProcessMemory`；配置页只读时（`native_force=1`）临时改成可写再改回来，
  每次都会记日志。

这样血量由游戏自己的系统去涨，它另存的那份拷贝也会一起更新，**不需要再扫描内存，也就没有扫描带来的掉帧**。

## 部位回血开关（v0.14 起按布局检查启用）
部位有自己的一位开关：`DamageableZoneInfo.RegenerationEnabled`（datalibrary 注释：护盾/部位在回血冷却结束后回血）。
v0.14 从 filediver 的字段顺序和已有锚点推导 `+0x13d`，逐部位验证后启用。部位选择由 `part_regen` 和 `part=` 控制。

发 `parts` 查看每个部位的实际开关和布局检查。`healcfg` 仍会打印**候选偏移**并导出 `0x5650` 字节配置，
但布尔候选不能证明布局或修复成功。旧设置文件如含 `native_zone=0`，需要改为 `0x13d` 并发 `reload` 才会使用新路径。

普通再生是否会复活死亡部位、触发回血事件并恢复模型/物理，仍待当前游戏中验证。完整依据与实验步骤见 [部位再生.md](部位再生.md)。

## 已知限制
- 配置表按单位资源共享：开关打开期间，**同种载具**（包括不在罩子里的、别人的）也会回血；
  载具一离开罩子就写回原值，所以影响只限罩子开着的那段时间。
- 主血量及开启原生再生的部位由游戏回血；车体网络血量仍由 `net_heal` 处理。
  未启用原生再生且未被独立禁用的部位保留旧的回填路径（含 `hull_zones`）。
- 联机时只有本机有权威的载具会受影响，和以前一样。
- `heal=write` 可以切回旧的逐帧写血量（没有扫描），用来对照或兜底。

## 怎么在游戏里确认
- `hptrace 20`：每 0.5 秒记一次主血量 / 部位和 / 配置开关状态。把载具停在罩子里，
  看主血量是不是在涨、日志里配置是不是 `open`。
- `healcfg`：看配置头当前值和候选偏移。
- `status`：能看到 `native_open=` 和 `forced=`（走“临时改页保护”写了几次）。
